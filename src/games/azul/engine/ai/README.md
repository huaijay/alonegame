# 花砖物语 AI

## 搜索契约

`chooseMove(state, options)` 使用 Max-n。轮到哪位玩家，就选择使该玩家收益最大的后续行动。它支持项目中的两人、三人和四人局。

- `depth` 表示根行动之后最多继续搜索的玩家行动数。根候选会先各自执行一次正式规则转移，因此 `depth: 0` 已包含本次行动和可能触发的轮末结算。
- 搜索从一层开始迭代加深。只有所有根候选都完成这一层，才更新候选价值；中断时保留上一完整层。
- `Decision.depth` 是所有根候选实际完成的深度，`requestedDepth` 是请求深度，`interrupted` 表示预算阻止了下一完整层。
- `nodes` 包含递归访问、叶子和缓存命中，不包含根候选的静态估值；它严格不超过 `nodeBudget`。`cacheHits` 单独记录置换表命中次数。
- 计时从生成根候选之前开始。零时间或零节点预算仍会完成所有根候选的静态估值，返回合法走法；JavaScript 调度、垃圾回收和一次规则转移不能作硬实时保证。
- 深度、节点预算必须是非负安全整数，时间预算必须是非负有限数，否则抛出 `RangeError`。非 `placing` 阶段或没有合法行动时返回 `null`。

### 下轮补砖边界

当前工厂盘和中央供应完全已知，搜索在这些信息上展开。行动耗尽供应时，使用正式规则完成上墙、扣分及终局判断。如果仍可补砖，搜索停在已结算的 `roundEnd`，交给估值器处理未来潜力。只有砖袋与弃砖均为空时，才直接确认流通砖耗尽的终局。

AI 不调用真实对局随机源。真正补盘由会话或批量对局传入 `createRng(seed)` 完成。轮末的估值使用下一次补砖的颜色期望数量，不构造一套确定的未来工厂盘。

为避免通过弃砖无限拖延败局，搜索会单独检查可证明的整轮自循环：仅当下一次抽取会拿完整个流通池，或池中只剩一种颜色时，才比较补盘后的完整局面。当前规则按抽到的五色数量排序后切盘，因此这两种情况的补盘完全确定。比较包含当前玩家、分数、图案行、墙、地板、先手和各处砖数，仅忽略展示用轮号及等价工厂编号。

如果还有不会返回原局面的合法行动，内部搜索跳过自循环；根层保留该候选，标记 `repeatsPosition: true`，并以 `-1_000_001` 将其排在普通终局之后。这是确保行动有进展的策略值，不是正式规则判负。若全部行动都是自循环，仍返回合法行动及静态价值，不制造终局。以后若改变补盘为保留随机抽取顺序的分盘方式，必须重新审查这项确定性前提。

### 同分与候选解释

同分容差为 `1e-9`。内部按工厂盘的颜色数量排序，再按颜色、目标行排序，合并内容相同的工厂盘。根层保留全部真实工厂编号及合法行动，同分时保留原来的枚举顺序，界面仍可展示每个真实来源。

`Candidate.value` 来自最后一轮完整搜索。`Candidate.breakdown` 解释该根行动刚执行后的静态局面；深度大于零时，它的 `total` 可以与搜索价值不同。

## 规则和性能结构

`applyMove` 与 `applyMoveState` 共用一套规则核心：

- `applyMove` 为界面生成拿砖、放置、扣分和上墙等动画快照。
- `applyMoveState` 只返回行动结果，不创建动画步骤；轮末会结算，但不补下一轮工厂。
- `advanceState` 在上述结果上补盘，供完整自动对局使用。

普通行动只复制被修改的玩家板、目标图案行和工厂盘，未变化部分作为只读数据共享。全员结算前会复制全部玩家板。调用方应把输入和返回状态都视为不可变值；需要自行修改时先用 `cloneState`。

搜索的置换表按剩余深度分层，每次决策最多保存 32,768 个内部节点。键包含行动玩家、先手、中央标记、轮次、供应、砖袋、弃砖、图案行、地板颜色和墙面。工厂内容排序后进入键，工厂编号不影响等价局面的价值；座位和工厂数量在单次决策内固定。

玩家板与工厂签名按不可变对象引用复用。叶子直接估值，避免为低复用率的叶子保存置换表。每次 `createEvaluator()` 都拥有独立工作区，为最多四位玩家各保留一个板面特征槽：引用未变时复用结果，变化时原地覆写预分配的记录。供应、储备与先手仍逐局面计算。缓存大小固定，返回的数组及解释对象不引用内部缓冲区。

## 估值依据

规则数值继续以项目当前的 `rules.ts`、`board.ts` 和规则测试为准。共享 `scoreForCell` 与 `endgameBonus`，使估值和真实结算采用同一套计分函数。

1. **已入账分数**：每一实际分值换算为 10 个估值单位。
2. **已满图案行**：按正式结算的行顺序投影到墙面，计算准确的上墙收益；后上墙的砖可以利用前面刚建立的连接。
3. **未满图案行**：综合填充比例、缺砖数量、当前可见供应及储备，折算未来完成价值。若任一玩家将在本轮完成整条墙行，停止预支以后轮次的储备价值。
4. **墙面**：计入投影墙的现行终局奖励，并给连片结构一个较小修正。同色多条未满行取最高的奖励潜力，避免重复预支同一份颜色奖励。
5. **地板**：按项目实际结算顺序，先根据当前分数计算触底后的扣分，再计算上墙得分。
6. **先手**：本轮确定获得下轮先手时增加少量机会价值；最终轮不再计算。
7. **竞争关系**：对手分项取平均后乘以 0.85，再从自己对应分项中扣除，使多人局不会仅因人数增加而成倍放大对手权重。

非终局分项合成为：

```text
total = score × 10 + rows + wall + floor × 10 + marker
```

终局直接以正式规则给出的 `state.winner` 为准，包含同分时的座位裁决：胜者为 `+1_000_000`，其他玩家为 `-1_000_000`。此时解释对象的 `score` 和 `total` 都是终局值，不再套用上述乘法。

未满行完成率、结构价值、先手机会与竞争权重属于启发式。分数用于比较行动，不能当成胜率；可见颜色数量也不保证这些砖最终都能由同一玩家取得。深度和轮末信息边界决定了搜索的实际覆盖范围。

## 会话与规则修复

每次新轮开始，中央首玩家标记都会重新放回。动画队列播放完后，会话提交正式行动的最终状态，再保存回放帧，保证换人、补盘和终局标记与规则结果一致。重开时清空待提交状态并重置结束通知，结束回调每局只触发一次。会话定时器使用 `globalThis`，可在 Node 中推进完整对局。

## 验证与复现

在项目根目录运行，使用现有依赖：

```sh
pnpm typecheck
pnpm test
pnpm build
pnpm bench:azul:budgets
pnpm bench:azul --depth 2 --warmup 3 --rounds 7 --out .ai-work/azul-depth2.json
```

`tests/azul/reachable-positions.json` 固定了修改前规则下两人、三人、四人的真实对局开局、中盘和接近轮末的局面，用于新旧引擎在相同输入上的比较。修复后的在线可达轨迹另由有种子对局和规则差分覆盖。基准同时提供使用相同估值、同一轮末边界的独立 Max-n 穷举：它调用带动画的 `applyMove`，没有置换表和等价工厂合并。

如修改前快照仍保存在 `.ai-work/azul-20261117/original/engine`，基准会同时测量原版；也可用 `--baseline` 指定另一份完整引擎中的 `ai/search.ts`。原版的估值和跨轮搜索边界不同，因此原版与新版的时间比较表示端到端表现；同估值穷举用于检查实现本身的收益。

`--names` 可筛选逗号分隔的局面名，`--skip-naive` 可跳过重复的穷举计时，`--current` 可指定待测引擎快照。原版快照存在时，可运行固定节点预算对战：

```sh
pnpm bench:azul --depth 2 --skip-benchmark --match-groups 20 --players 2 --match-nodes 3000 --out .ai-work/azul-matches-2p.json
pnpm bench:azul --depth 2 --skip-benchmark --match-groups 10 --players 4 --match-nodes 3000 --out .ai-work/azul-matches-4p.json
```

每个种子把新版轮换到全部座位，其余玩家使用原版；双方具有相同请求深度和节点预算。对战时间上限放宽以保证复现，真实补盘共用当前正式规则及固定随机种子。报告保留每局的座位、比分、赢家、轮数和实际搜索深度。有限种子对局反映这些条件下的表现，不等于 Elo。

预算脚本分别检查界面的 200 ms / 120,000 节点和批量模式的 8 ms / 3,000 节点，记录实际完成深度、节点数和延迟。请求深度不代表每个局面都能在预算内完成。

回归覆盖全候选独立穷举、预算中断、冻结输入、工厂置换、无动画与动画转移一致、首玩家标记、终局同分裁决、估值分项及完整会话重开。项目 `AGENTS.md` 另外要求浏览器深色、浅色主题各完成一局；这项应在已连接的浏览器中单独验收。
